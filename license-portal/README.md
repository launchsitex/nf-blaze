# NF-Blaze · פורטל ניהול רישיונות

אתר פרטי (לא לאינדוקס) להנפקת מפתחות רישיון ל-NF-Blaze ולשמירת רשימת הלקוחות.

- **פרויקט Supabase:** `ilsidpixxkfwowsnkntg`
- **חשבון אחד בלבד** — ההרשמה נפתחת פעם אחת, ואחרי יצירת המנהל היא נחסמת לצמיתות.
- **המפתח הפרטי לעולם אינו בדפדפן** — החתימה נעשית ב-Edge Function בצד השרת.

## מבנה

```
license-portal/
├── index.html                      האתר עצמו (עמוד יחיד, עברית RTL)
├── config.js                       כתובת הפרויקט + מפתח anon (לא סוד)
└── supabase/
    ├── migrations/0001_license_portal.sql   טבלת nfb_licenses + RLS
    └── functions/
        ├── admin-bootstrap/        יצירת המנהל היחיד + בדיקה אם ההרשמה עוד פתוחה
        ├── issue-license/          חתימת Ed25519 ושמירת הרישיון
        ├── validate-license/       אימות מקוון + ספירת מושבים
        ├── request-license/        טופס «בקשת רישיון» מדף הנחיתה
        └── submit-feedback/        משוב ודיווחי תקלות מהאפליקציה
```

## שחזור גישה אם חשבון המנהל אבד

נעילת ההרשמה היא דגל קבוע במסד — היא **לא** נגזרת מקיום המשתמש, כדי שמחיקת
חשבון לא תפתח את ההרשמה לכל מי שמגיע לאתר. אם החשבון אבד, פתח את הנעילה
ידנית ב-SQL Editor והירשם מחדש:

```sql
update public.nfb_portal_state set admin_bootstrapped = false;
```

## התקנה — לפי הסדר

### 1. מסד הנתונים

הרץ את `supabase/migrations/0001_license_portal.sql` (SQL Editor או `supabase db push`).

### 2. הסוד: המפתח הפרטי לחתימה

**זה השלב היחיד שחייב להיעשות ידנית, והוא קריטי.** בלעדיו הנפקת מפתחות לא תעבוד.

Supabase → Project Settings → Edge Functions → Secrets → הוסף:

| שם | ערך |
|----|-----|
| `LICENSE_PRIVATE_KEY` | כל התוכן של `secrets/license-private.pem`, כולל שורות ה-BEGIN/END |
| `LICENSE_PUBLIC_KEY` | כל התוכן של `secrets/license-public.pem` (לאימות מפתחות נכנסים ב-`validate-license`) |

⚠️ המפתח הזה הוא **הנכס הקריטי ביותר** של מערכת הרישוי. מי שמשיג אותו יכול
להנפיק רישיונות בעצמו. אין להעלות אותו לגיט ואין לשלוח אותו בצ'אט או במייל.

### 3. פריסת ה-Edge Functions

```bash
supabase functions deploy admin-bootstrap --no-verify-jwt
supabase functions deploy issue-license
supabase functions deploy validate-license --no-verify-jwt
supabase functions deploy submit-feedback --no-verify-jwt
```

`validate-license` ו-`submit-feedback` נקראות מהאפליקציה (בלי JWT — היא מזדהה
דרך חתימת המפתח, לא דרך התחברות משתמש). שתיהן דורשות את הסוד
`LICENSE_PUBLIC_KEY` כדי לאמת את המפתח הנכנס.

`admin-bootstrap` חייב לרוץ בלי JWT — הוא נקרא לפני שקיים משתמש בכלל.
הוא מגן על עצמו: אחרי שנוצר מנהל, כל קריאה נוספת מוחזרת עם 403.

### 4. חסימת הרשמה ציבורית ב-Supabase Auth

Authentication → Providers → Email → **כבה** "Enable sign-ups".

בלי זה, כל אחד שמכיר את מפתח ה-anon יכול לפתוח חשבון דרך ה-API ולעקוף את
מסך ההרשמה שנחסם באתר. **זה נבדק בפועל ואומת:** קריאה ישירה ל-`/auth/v1/signup`
עם מפתח ה-publishable יצרה משתמש חדש בהצלחה. מפתח ה-publishable נמצא ב-`config.js`
שמועלה לשרת, כלומר הוא גלוי לכל מי שפותח את קוד המקור של העמוד.

### 5. הגדרות האתר

ערוך את `config.js` והדבק את מפתח ה-anon (Project Settings → API).
המפתח הזה אינו סוד — הוא מיועד לדפדפן ומוגן ב-RLS.

### 6. העלאה לאוויר — שני קבצים בלבד

**מעלים לשרת רק את אלה, ישירות בשורש התיקייה באתר:**

```
index.html
config.js
.htaccess     (אופציונלי — רק לאחסון מבוסס Apache כמו Hostinger)
```

`.htaccess` מונע מהדפדפן להחזיק גרסה ישנה של העמוד. בלעדיו, אחרי כל עדכון
צריך רענון קשה (`Ctrl+Shift+R`) — אחרת ה-JavaScript הישן פונה למסד עם סכמה
חדשה ומקבל `permission denied`.

**לא מעלים** את `supabase/` (המיגרציה והפונקציות נפרסות לתוך Supabase, לא
לאחסון האתר) ולא את `README.md`. העלאה שלהם לא תשבור כלום, אבל היא חושפת
מידע פנימי לכל מי שינחש את הכתובת.

כל אחסון סטטי מתאים — Hostinger, Vercel, Netlify. אין שלב build.

**האתר לא אמור להיות ציבורי:** יש בו `noindex, nofollow`, אבל מומלץ גם
כתובת לא מנוחשת (למשל תת-דומיין ייעודי) וכניסה עם סיסמה חזקה.

## משוב ממשתמשים (מ-02.08.2026)

טאב **«משוב ממשתמשים»** מציג פניות שנשלחו מתוך NF-Blaze דרך כפתור «משוב»
שבסרגל העליון של האפליקציה.

- **סוגי פנייה:** תקלה · שיפור · משוב · שאלה · **בקשת/חידוש רישיון**. סינון
  לפי סוג ולפי סטטוס (פתוחות / טופלו / הכל), ומונה פניות חדשות על הטאב עצמו.
- כל פנייה מציגה כותרת ותוכן, **שם השולח**, אימייל לחזרה אם הוזן,
  **תאריך ושעה**, וגרסת המערכת ומערכת ההפעלה של השולח.
- סטטוס: חדשה → בטיפול → טופל (וניתן להחזיר לפתוחה). **הסטטוס פנימי ואינו
  נשלח ללקוח** — אין כרגע ערוץ תשובה מהפורטל; חוזרים ללקוח במייל.
- פנייה ארוכה מוצגת מקוצרת עם «הצג הכל».

הטבלה: `nfb_user_feedback`, מיגרציות `0006_user_feedback.sql` ו-
`0007_feedback_unlicensed.sql`.

### 🔒 «מאומתת» מול «לא מאומתת» — הדבר החשוב במסך הזה

| | מאומתת | 🚩 לא מאומתת |
|---|---|---|
| נשלחה | ממחשב עם רישיון פעיל | ממחשב בלי רישיון |
| מקור השם | **מפתח הרישיון החתום** — נגזר בשרת | **מה שהפונה הקליד** |
| אפשר לסמוך על הזהות | כן | **לא** |

האפליקציה שולחת את **מפתח הרישיון החתום**, לא את השם. ‏`submit-feedback`
מאמתת את חתימת ה-Ed25519 מול `LICENSE_PUBLIC_KEY`, מחלצת את מזהה הרישיון,
ומושכת את השם מ-`nfb_licenses`. לכן **אי אפשר לשלוח פנייה בשם לקוח אחר**.

מי שאין לו רישיון יכול לשלוח בכל זאת — אחרת מי שתקוע בשער הרישיון לא יכול
לבקש חידוש בשום דרך מתוך המערכת. פנייה כזו מסומנת בתגית **«לא מאומתת»**
בטבלה, ושם ואימייל הם בה שדות חובה. אל תנפיק רישיון על סמך פנייה לא
מאומתת בלי לאמת מול הלקוח בדרך אחרת.

מפתח פגום **אינו** נופל לפנייה אנונימית — הוא נדחה. אחרת אפשר היה לעקוף
את השיוך בכוונה על ידי שליחת זבל בשדה המפתח.

הכנסה לטבלה אפשרית רק ב-`service_role` — לא מהדפדפן.

### מגבלת קצב

**פנייה אחת לכל 3 שעות, לכל כתובת IP** — כולל בעלי רישיון. נשמרת בטבלה
`nfb_feedback_throttle` (גיבוב של הכתובת, לא הכתובת עצמה) ונבדקת אטומית
ב-`nfb_feedback_throttle_check`. **בכוונה במסד ולא בזיכרון:** מגבלה בזיכרון
לא שורדת מיחזור אינסטנס, ולכן לחלון של 3 שעות היא חסרת ערך.

⚠️ שתי השלכות: משרד שכל המחשבים בו יוצאים דרך אותה כתובת חולק מכסה אחת,
ולקוח ששלח דיווח לא יוכל לשלוח לו המשך במשך 3 שעות. להחרגת בעלי רישיון —
לדלג על הבדיקה כשקיים `verified` ב-`submit-feedback`.

לשינוי החלון: `THROTTLE_WINDOW_SECONDS` ב-`submit-feedback/index.ts`.
אפשר גם להגדיר סוד `FEEDBACK_IP_SALT` לגיבוב הכתובות (יש ברירת מחדל).

⚠️ **אין התראה על פנייה חדשה** — צריך להיכנס לפורטל כדי לראות אותה.

## ניהול מחשבים ומכסה (מ-02.08.2026)

בטאב **«רישיונות»**, לכל לקוח יש שתי עמודות חדשות:

- **מחשבים** — כמה מכונות תפוסות מתוך המכסה (`2 / 3`). המספר מסומן באדום
  כשהמכסה מלאה. לחיצה פותחת את הרשימה: שם המחשב, מתי נראה לאחרונה, מתי
  נרשם, כתובת IP וטביעת האצבע — עם כפתור **«שחרר מחשב»**.
- **מכסה** — שדה לעריכה ישירה. `0` = ללא הגבלה.

**רישיון חדש = מחשב אחד** (ברירת המחדל של `seats` היא 1 מ-`0008`).
⚠️ **רישיונות שהונפקו קודם נשארו על 3** — שינוי ברירת המחדל אינו נוגע
בשורות קיימות, בכוונה: הורדה גורפת ל-1 הייתה נועלת מיד כל לקוח שעובד על
יותר ממחשב אחד. לצמצום לקוח מסוים — פשוט ערוך את המכסה שלו בטבלה.

### מתי צריך לשחרר מחשב

לקוח שפירמט, החליף מחשב או שדרג חומרה **ייחסם** עם «הרישיון בשימוש
במחשבים אחרים», כי הטביעה החדשה שונה. משחררים את הישן מהרשימה, והוא נכנס
באימות הבא (עד 5 דקות, או מיד בלחיצה על «בדוק שוב» במסך החסימה).

### 🔒 למה טביעת אצבע ולא כתובת IP

הזיהוי הוא `machineFingerprint()` — ‏`sha256(hostname|user|platform|arch)`.
כתובת IP **לא מתאימה לאכיפה**: היא מתחלפת בכל אתחול ראוטר, שונה בבית
ובמשרד, ומשותפת לכמה לקוחות ב-CGNAT — כלומר הייתה נועלת לקוחות משלמים כל
כמה ימים בלי לעצור תוקף אמיתי. הכתובת **כן** נשמרת ב-`last_ip`, אבל רק
כדי לעזור לזהות «איזה מחשב זה» ברשימה.

⚠️ **מגבלה ידועה:** הטביעה נגזרת משם המחשב + שם המשתמש + פלטפורמה. מי
שישכפל את שניהם במחשב אחר יקבל אותה טביעה.

## שימוש יומיומי

1. כניסה עם האימייל והסיסמה שהוגדרו בהרשמה הראשונה.
2. **יצירת רישיון:** שם מלא של הלקוח (זה השם שיוצג לו במסך הכניסה
   ל-NF-Blaze — «ברוך הבא נתנאל»), תאריך תוקף או «ללא הגבלת זמן», ולחיצה על
   «צור רישיון».
3. המפתח מוצג להעתקה ונשמר בטבלה למטה עם שם הלקוח ותאריך היצירה.
4. הלקוח מדביק את המפתח במסך הכניסה של NF-Blaze.

## מה עדיין לא קיים

- **חסימת רישיון קיים** — הטבלה כבר מכילה `revoked` / `revoked_at`, אבל אין
  ממשק ואין לוגיקה. שים לב שחסימה אמיתית מחייבת שינוי גם באפליקציה: היום
  אימות הרישיון הוא **אופליין לחלוטין**, ולכן חסימה במסד הנתונים לא תשפיע על
  לקוח שכבר הפעיל מפתח. יידרש מנגנון בדיקה מול השרת (עם תקופת חסד לעבודה
  אופליין). זה השלב הבא שסוכם עליו.
